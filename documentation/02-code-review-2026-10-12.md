## A. Review of `c5ccaf9` / `1509601`

### 1. High — Email events stuck for 10 minutes after any transient error; BullMQ retries silently dropped
`src/lib/services/email-event-service.ts:611`

On `RetryableEmailError` the event stays `PROCESSING` with a fresh `lastAttemptAt`. Both the new conditional claim and the new `findPendingEvents` filter skip it for 10 minutes. A retry in that window gets `{success: true, skipped: true, reason: 'CONTENTION_LOCK_HELD'}`, so BullMQ marks the job complete and never retries. Bounce/complaint suppression is delayed by at least 10 minutes. Before this commit the next tick picked it up.

**Fix:** on a retryable failure, set the event back to `RECEIVED` (or a `RETRYING` state with `nextAttemptAt`) and clear the lock, instead of leaving it `PROCESSING`.

### 2. High — Contention yields keep increasing `attemptCount`, so jobs fail permanently on their first real error
`src/lib/services/serverless-job-processor.ts:268`

The claim increments `attemptCount` (line 174). The contention-yield path puts the job back to `QUEUED` but does not decrement it, and nothing caps the number of yields. The time-exhausted release path does decrement. A job waiting on a held item yields about every 5 s for up to 10 min, so `attemptCount` runs far past `maxAttempts`. The first real `RetryableError` then hits `reachedMax` and the job fails with `MAX_ATTEMPTS_EXCEEDED`.

**Fix:** decrement `attemptCount` on yield (same as the time-exhausted path), and delay the next attempt with backoff rather than 5 s.

### 3. High — Campaign retry sends the email twice, then marks the recipient FAILED
`src/lib/services/executors/campaign-recipient-executor.ts:296`

`emailDelivery.create` now uses a fixed `idempotencyKey`, and `EmailDelivery` has `@@unique([clientId, idempotencyKey])`. If attempt 1 sends and creates the row but a later step throws, the recipient goes back to `PENDING`. Attempt 2 calls `provider.send` again (duplicate email). `create` then fails with P2002, which is classified as permanent, so the recipient is marked `FAILED` and the campaign counts are wrong.

**Fix:** before sending, look up an existing `EmailDelivery` by `(clientId, idempotencyKey)`. If it exists, skip the send and finish the bookkeeping. Treat P2002 on create as "already sent".

### 4. High — Provider-level idempotency does not exist: Gmail ignores `idempotencyKey`
`src/lib/services/executors/email-delivery-executor.ts:273` (also `campaign-recipient-executor.ts:288`)

The only email provider (`src/lib/email/providers/gmail/`) never reads `idempotencyKey`. If the function is killed after Gmail accepts the message but before the `SENT` update, the stale-lock reclaim after 10 minutes sends it again.

**Fix:** Gmail has no idempotency API, so this has to be solved locally. Write a `SENDING` marker with the key before calling Gmail. On reclaim, don't re-send a `SENDING` row older than N minutes; mark it `UNKNOWN` for manual review instead. Also update the docs so they no longer claim provider idempotency.

### 5. Medium — Permanently FAILED deliveries can be claimed and re-sent
`src/lib/services/executors/email-delivery-executor.ts:70`

The terminal-state guard leaves out `FAILED`, and the new claim explicitly re-claims `FAILED` rows with `attemptCount < maxAttempts`. A delivery rejected as permanent (suppressed, empty content, provider rejection) can be sent again by a duplicate or re-driven job.

**Fix:** treat `FAILED` as terminal, as `CampaignRecipientExecutor` already does.

### 6. Medium — Attempt count is off by one on the sweep path
`src/lib/services/executors/email-delivery-executor.ts:170` (also `campaign-recipient-executor.ts:151`)

When a `claimToken` is passed, the sweep SQL has already incremented `attemptCount`, and the executor adds 1 again. The first transient error on real attempt 4 of 5 becomes permanent, and backoff is one step too long.

**Fix:** when `claimToken` is present, use `attemptCount` as-is.

### 7. Medium — Campaign recipients stuck in PROCESSING forever on early errors
`src/lib/services/executors/campaign-recipient-executor.ts:244`

After the claim, several exits throw without releasing the lock: campaign not found (167), no template version (206), unverified sender (232), and `resolveForTenant` throwing (244/257, outside the `try`). The sweep only selects `PENDING`/`RETRYING`, so the recipient is never picked up again and the campaign stays `RUNNING` forever.

**Fix:** wrap everything after the claim in `try/finally`. On error, set the recipient to `FAILED` (permanent) or `RETRYING` (transient) and clear the lock.

### 8. Medium — Final writes are not bound to the claim token
`src/lib/services/executors/email-delivery-executor.ts:311` (also 334; recipient executor 353/375)

The `SENT`, retry and failure updates filter on `id` (or `status=PROCESSING`) only. A worker that lost its lock to a stale reclaim can overwrite the new owner's state and cause another send.

**Fix:** add `lockedBy: claimToken` to every post-claim `updateMany` and check `count`.

### 9. Low — Dead `FAILED` clause in the recipient claim
`src/lib/services/executors/campaign-recipient-executor.ts:100`

`{ status: 'FAILED', attemptCount: { lt: maxAttempts } }` can never match, because line 73 already returns early for `FAILED`. Remove the clause.

### 10. Low — Claim logic copy-pasted in 3 services; 10-minute stale timeout hard-coded in 7+ places
`email-delivery-executor.ts:102`, `campaign-recipient-executor.ts`, `email-event-service.ts`, SQL sweeps, `reconcileJobs`

The copies already disagree (the event claim has no attempts cap and can't reclaim rows with `lastAttemptAt = null`). Extract one `claimRow()` helper with a single `STALE_LOCK_MS` constant.

## B. Additional findings (config, routing, queue selection)

### 11. High — Processor endpoint returns HTTP 200 even when processing failed
`src/app/api/internal/process-jobs/route.ts:53-60`

The route always returns `{ success: true, data: result }` with status 200, even when `result.success === false` (e.g. reconciliation failed). The cron health check (`net._http_response` status codes) therefore **cannot detect processing failures**. "36/36 HTTP 200" in the executive audit only proves the endpoint is reachable and authenticated.

**Fix:** return `success: result.success` and a 500 (or 207) status when `result.errors.length > 0`.

### 12. High (deployment trap) — Setting a remote `REDIS_URL` silently stops all async email
`src/lib/email/queue/queues.ts:25-31`

`isWorkerlessMode()` returns `false` when `REDIS_URL` points to a non-local host, unless `WORKERLESS_MODE=true`. Jobs then go into BullMQ, and nothing in production consumes BullMQ. `.env.example` says Redis is "used only for rate limiting", which encourages exactly this setup.

**Fix:** set `WORKERLESS_MODE=true` in Vercel, or don't set `REDIS_URL` at all (rate limiting falls back to Postgres). Better still, make workerless the default in production.

### 13. High (if campaigns are used) — Unsubscribe and tracking links fall back to fake domains
- `campaign-recipient-executor.ts:268` uses `NEXTAUTH_URL`, falling back to `https://app.whatsapphub.internal`
- `email-tracking-service.ts:277,322`, `campaign-worker.ts:352` and `promotional-delivery-worker.ts:120` use `NEXT_PUBLIC_APP_URL`, falling back to `https://hub.local`

Neither variable is in `.env.example`, and everything else uses `APP_URL`. If they're unset, every `List-Unsubscribe` header and tracked link is broken. That breaks unsubscribe compliance and hurts Gmail deliverability.

**Fix:** use `env.APP_URL` everywhere. Until then, set both variables in Vercel to `https://promotions-lime.vercel.app`.

### 14. Medium — `.env.example` uses the wrong names for email secrets

| `.env.example` says | Code actually reads |
|---|---|
| `GOOGLE_CLIENT_ID` | `GMAIL_CLIENT_ID` |
| `GOOGLE_CLIENT_SECRET` | `GMAIL_CLIENT_SECRET` |
| `PROVIDER_CREDENTIAL_KEY` | `EMAIL_CREDENTIALS_ENCRYPTION_KEY` (falls back to `WEBHOOK_SECRET_ENCRYPTION_KEY`) |
| *(missing)* | `WEBHOOK_SECRET_ENCRYPTION_KEY`, **required in production** by `env.ts` |

Someone following the example would set variables the code ignores. The Gmail OAuth callback would then fail with "client secret missing".

### 15. Low — OAuth endpoints accept the Google client secret as a URL query parameter
`src/app/api/admin/email/providers/google/callback/route.ts:118`

`googleClientSecret` can come from `?googleClientSecret=…`, which puts the secret in browser history and access logs. The routes are Admin-only, so the risk is low. Read it only from the environment.
